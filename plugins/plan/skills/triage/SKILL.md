# Triage

Move issues through a state machine of triage roles. The issue tracker is Jira. Fetch a ticket as context with `/jira:ticket`.

Passion repos are not open to external contributors, so pull requests are **out of triage scope** by default and the deltas marked "for a PR" below do not apply. When the maintainer puts PRs in scope for a repo, **a PR is an issue with attached code** — the same machine runs.

Every comment and issue you post during triage **must** start with this disclaimer:

```
> *This was generated by AI during triage.*
```

## Roles

Two **category** roles:

- `bug` — something is broken
- `enhancement` — new feature or improvement

Five **state** roles:

- `needs-triage` — maintainer needs to evaluate
- `needs-info` — waiting on reporter for more information
- `ready-for-agent` — fully specified, ready for an AFK agent
- `ready-for-human` — needs human implementation
- `wontfix` — will not be actioned

For a PR: `ready-for-agent` means a brief is attached and an agent takes the next step on the diff; `ready-for-human` means a human should merge.

Every triaged issue should carry exactly one category role and one state role. If state roles conflict, flag it and ask the maintainer before doing anything else.

These are canonical role names; the label strings in the project's Jira may differ. Read the labels the project already uses — every label you apply comes from that list. Ask the maintainer when the mapping is not obvious.

State transitions: an unlabeled issue normally goes to `needs-triage` first; from there it moves to `needs-info`, `ready-for-agent`, `ready-for-human`, or `wontfix`. `needs-info` returns to `needs-triage` once the reporter replies. Flag transitions that look unusual and ask before proceeding.

## Invocation

The maintainer describes what they want in natural language: one of the branches below, or an ad-hoc query against the tracker ("what's ready for agents to pick up?").

## Show what needs attention

Query the issue tracker and present three buckets, oldest first:

1. **Unlabeled** — never triaged.
2. **`needs-triage`** — evaluation in progress.
3. **`needs-info` with reporter activity since the last triage notes** — needs re-evaluation.

When PRs are in scope for a repo, include them and tag each line `[PR]` or `[issue]`. Discovery skips PRs opened by people with write access — a colleague's in-flight PR is not triage work — but a PR the maintainer names is always triaged.

Show counts and a one-line summary per item. Let the maintainer pick.

## Triage a specific issue or PR

1. **Gather context.** Read the full issue or PR (body, comments, labels, author, dates; for a PR, the diff too). Where prior triage notes exist, carry their settled points forward and check whether the reporter has answered the outstanding questions. Explore the codebase using the project's domain glossary, respecting ADRs in the area. Run two checks: (a) **redundancy** — search for an existing implementation of the requested behavior, matching by domain concept rather than the request's wording, and report where you looked. If found, it's an already-implemented `wontfix` (step 5). (b) **prior rejection** — run the same concept match against `.out-of-scope/*.md` and surface any hit to the maintainer ([OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)).

2. **Recommend.** Tell the maintainer your category and state recommendation with reasoning, plus a brief codebase summary relevant to the request — including whether it's already implemented. Wait for direction.

3. **Verify the claim.** For a bug, reproduce it from the reporter's steps. For a PR, check the diff out and run the relevant tests or commands. Report one of three outcomes: confirmed (with the code path), failed, or insufficient detail (a strong `needs-info` signal).

4. **Grill (if needed).** When the request is too thin to write acceptance criteria from, run `/general:grilling` and `/plan:domain-modeling` together — sharpening domain terms and updating `CONTEXT.md`/ADRs inline as decisions land.

5. **Apply the outcome:**
   - `ready-for-agent` — post an agent brief comment ([AGENT-BRIEF.md](AGENT-BRIEF.md)).
   - `ready-for-human` — an agent brief plus why it needs a human (judgment calls, external access, design decisions, manual testing).
   - `needs-info` — post triage notes (template below).
   - `wontfix` — close with a comment that fits the reason:
     - **Already implemented** — point to where the behavior already lives.
     - **Rejected bug** — explain the decision.
     - **Rejected enhancement** — write to `.out-of-scope/` and link it from the comment ([OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)).
   - `needs-triage` — apply the role. Optional comment if there's partial progress.

   Every comment and `.out-of-scope/` file goes through `/general:to-ste` in `flavored` mode before it is posted — ticket prose, not a runbook. Quoted reporter language, log excerpts, and identifiers stay exactly as written. The outcome is applied once that pass has run.

## Quick state override

When the maintainer says "move #42 to ready-for-agent", apply the role directly. Confirm what you are about to do (role changes, comment, close), then act. For a move to `ready-for-agent`, ask whether they want an agent brief written.

## Needs-info template

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

Capture everything settled during grilling under "established so far" so the work isn't lost. Each question names the specific fact that is missing and why it blocks triage.
