# Onboarding runs through Claude Code itself

Setup is one sentence pasted into Claude Code — the person's department plus a link to `ONBOARDING.md` in this repo. Claude reads the document, merges the settings into whatever `~/.claude/settings.json` already exists, walks the person through obtaining a Jira API token, writes `~/.claude/passion.env`, and checks for `uv`.

The whole install reduces to two keys in one file:

```json
{
  "extraKnownMarketplaces": {
    "passion-tech": {
      "source": { "source": "github", "repo": "passiondev/tech-skills" },
      "autoUpdate": true
    }
  },
  "enabledPlugins": { "local-engineering@passion-tech": true }
}
```

`autoUpdate` is documented as updating "this marketplace and its installed plugins on startup", so one flag delivers what [0001](0001-public-marketplace-repo.md) required. `enabledPlugins` takes `plugin@marketplace` keys, and [0002](0002-capability-plugins-and-department-bundles.md)'s dependency mechanism does the rest — naming the department bundle pulls in every capability plugin it needs.

*The last clause is false, and it was the first thing to break when the install was finally run. Tested against a clean `HOME` on Claude Code 2.1.222 with nothing but the settings block above: enabling `ops@passion-tech` installed `general`, its dependency `jira`, and eventually the `ops` bundle — and never installed `plan`. `ops` sat at `✘ failed to load` with `Dependency "plan@passion-tech" is not installed`, ten skills on disk against the fifteen the README promises. Four further startups converged on the same broken state; it does not self-heal. The pattern was identical for `local-engineering`: the first dependency's closure, then nothing. `claude plugin install <bundle>@passion-tech` resolves the full closure in one pass and repairs the broken state, so `ONBOARDING.md` now has an explicit install step with the expected plugin and skill counts per department.*

*One further correction, found by running the fixed document against a genuinely cold `HOME` rather than one already broken by a startup. Declaring a marketplace in `settings.json` does not make the CLI aware of it: on a machine that has never started Claude Code since the merge, both `claude plugin install` and `claude plugin marketplace update` fail with "not found in marketplace `passion-tech`" and "Available marketplaces:" — empty. The declaration is inert until something fetches it, which a startup does as a side effect and which `claude plugin marketplace add passiondev/tech-skills` does directly, reporting `(declared in user settings)` and leaving the file alone. So step 2 is two commands, and its ordering is the load-bearing part: the failure mode of getting it wrong reads as a missing plugin, which is the one diagnosis that sends a person back to check the manifest they cannot fix. Verified end to end on `analytics` with no SSH agent — 6 plugins, all `✔ enabled`, 28 skills, matching the table.*

*Two lessons, and the second is the uncomfortable one. Enabling a plugin and installing it are different operations, and the settings block only reliably does the first — `autoUpdate` maintains what is installed, it does not complete an install. And the "Considered options" below rejected an install script partly for being the only deterministic choice we were giving up; the actual remedy turned out to be neither a script nor a paste, but two commands run inside the interview, which keeps this ADR's shape while buying back the determinism.*

*The first clause of that paragraph survives testing, with one hole in it that is worth recording because nothing surfaces it. `autoUpdate` fetches on startup only when the startup is interactive. Measured on 6 August 2026 with the flag set and the clone two commits behind `main`: a `claude -p` run completed without fetching and left `lastUpdated` in `known_marketplaces.json` untouched, so nothing checked; an interactive start forty-eight seconds later wrote `FETCH_HEAD`, `known_marketplaces.json` and `installed_plugins.json`. Nothing was on `main` to pull by then, so what is directly observed for the interactive case is the fetch, not a fast-forward. The consequence is narrow and silent: anyone driving these skills from a script or a scheduled job never updates, and [0009](0009-no-plugin-versions.md)'s "whatever is on main is what everyone's next auto-update installs" quietly stops applying to them. `claude plugin marketplace update passion-tech` is the fallback, and the README and `ONBOARDING.md` now name it along with how to read the installed commit.*

*That last sentence named the wrong command, and the correction is the more useful finding. Measured on 7 August 2026 with the clone and all seven plugins at `065034b` and `main` at `72a3b10`: `claude plugin marketplace update passion-tech` moved the clone to `72a3b10` and left `installed_plugins.json` untouched — every plugin still registered at `065034b`, no cache directory for the new commit, and a cheerful `✔ Successfully updated marketplace`. The marketplace clone and the installed plugins are separate things, and only the second one executes. `claude plugin update <name>@passion-tech` is what moves a plugin, it fetches on its own so the marketplace command is not even a prerequisite, and it needs a restart to take effect. Two traps sit underneath. `claude plugin install <bundle>@passion-tech` is inert once installed — "already installed", nothing updated — so [0002](0002-capability-plugins-and-department-bundles.md)'s dependency closure, which this ADR already had to learn resolves on install, does not resolve on update. And `claude plugin update <bundle>@passion-tech` downloads all seven plugins and then registers only the bundle, leaving every capability plugin — which is where all the skills are — exactly where it was. Each plugin has to be named. The README and `ONBOARDING.md` now carry a loop over `claude plugin list`, and both retract the advice to read the commit with `git -C ~/.claude/plugins/marketplaces/passion-tech log`: that reads the clone, which is precisely the thing that sits ahead of what you are running. `claude plugin list` reports each plugin's own commit and was the right answer all along.*

*The block at the top of this ADR is now down to one key, and the reduction is the strongest evidence for the decision it documents. Measured on 12 August 2026 against a cold config: `claude plugin marketplace add passiondev/tech-skills` then `claude plugin install ops@passion-tech --scope user` produced four plugins, all `✔ enabled`, all `Scope: user`, fifteen skills on disk — with `enabledPlugins` written by the install, covering the bundle and all three dependencies, nobody having edited it. What the settings block still buys is `autoUpdate`, which `marketplace add` does not set because third-party marketplaces default to off. So the settings edit now comes after the install rather than before it, and it is one flag added inside an entry the CLI has already written. Which retires this ADR's own justification further down — "the actual difficulty here is merging two keys into a file that may or may not exist". The merge is the part that shrank. Everything that was hard is in the interview, which is where this ADR wanted it.*

*The restart between writing `passion.env` and using a skill was the next thing to break, and the report that surfaced it — that the skills "weren't available globally" — turned out to be a second fault wearing the same clothes. The restart goes first: `/reload-plugins` loads plugins, skills, agents and hooks into the running session, so the step that used to end the conversation now happens inside it. Two things it does read as failure and are not. Its summary counts a plugin's `commands/` directory, and every skill here lives in `skills/`, so it reports `0 skills` having loaded all of them. And where reloading would force a re-read of the conversation it warns and does nothing, which `--force` overrides. Neither is inferable from the output, so the document warns about both before asking — and it has to ask, because the agent cannot type a slash command on someone's behalf.*

*The globality half did not reproduce and is recorded here unconfirmed. `claude plugin install` defaults to `--scope user`, verified on the same cold config. But the interactive `/plugin` picker asks, and its other two answers write into a repo's `.claude/settings.json` or that one checkout, which is exactly the reported symptom: skills that work in the folder they were installed from and nowhere else. The document now passes `--scope user` explicitly despite it being the default, reads the `Scope:` line back for every plugin, and carries a troubleshooting row keyed on the symptom rather than the cause, because the symptom is the only part the person can see.*

*The rest of the feedback was not about correctness at all, and it is the half that matters more. People were completing the install and finishing it frightened. The permission prompts read as warnings; "get a Jira API token" assumed a page they had never seen; and everything they had been told lived in a chat log they were about to close. So the document now opens with a step that is purely talking — what the prompts are, what the three answers do, that Escape always works — placed before the first one can fire. It answers `--dangerously-skip-permissions` plainly rather than pretending nobody will raise it: built for throwaway containers rather than the laptop with their email on it, six approvals is not a problem worth that, and if they want it anyway it is their machine. The token is six numbered clicks with the wrong menu item named. And the last step writes a one-page reference to their machine and opens it in an editor, because a conversation is not a place to keep anything. This is the constraint the "executable documentation" note under Consequences did not anticipate: the document is read by an agent, but it is written for whoever is sitting in front of it, and the agent's most load-bearing instruction is to do one step and stop.*

Everyone installing this has Claude Code, by definition. That makes the agent the one tool the entire audience is guaranteed to have, on any operating system, with no script to write or keep working. And the actual difficulty here is merging two keys into a file that may or may not exist and may already contain anything — which is precisely what a copy-paste instruction handles badly and an agent handles well. Claude shows the diff before writing, so the person still sees what changed.

It also covers the parts a JSON block cannot. Getting a Jira API token means visiting Atlassian and creating one; `uv` may not be installed; `passion.env` needs six values a person has to gather. Those are an interview, not a paste.

## Considered options

- **Five copy-paste blocks in the README, one per department.** Transparent, nothing to maintain, nothing executed that was not read. Rejected on the known failure mode: someone with an existing `settings.json` replaces it rather than merging, or leaves a trailing comma, and it surfaces much later as "the plugin didn't install" with no visible cause. The block stays in `ONBOARDING.md` for anyone who prefers it — it is what Claude will be reading anyway.
- **An install script.** Deterministic and testable, which neither other option is. Rejected because it needs a PowerShell twin for anyone on Windows, and because it asks people to pipe a remote script into a shell — or to read it first, which is the step that gets skipped.

## Consequences

`ONBOARDING.md` is now executable documentation. It is read by an agent that will act on it, so vagueness there becomes wrong actions on someone's machine. It needs to state exactly which keys to merge and exactly what to leave alone.

Nothing about this is deterministic. Two people can run the same sentence and get different conversations, and there is no way to test the path the way a script could be tested. The mitigation is that the resulting state is checkable — `claude plugin list` shows what landed.

*That mitigation is what caught the dependency failure above, and it only worked because the document now states the number to expect. "They should see their department bundle plus its capability plugins" is not checkable — a person looking at four plugins when they should have seven has no way to know. A count is checkable, so step 2 carries one per department.*

The instruction includes a public URL, so it depends on the person's Claude Code being able to fetch it. Where it cannot, the document has to be pasted instead.
