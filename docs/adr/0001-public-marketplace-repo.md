# Host the marketplace in a public repo

The marketplace lives in the **public** repo `passiondev/tech-skills`, and people install it by adding `extraKnownMarketplaces` with `autoUpdate: true` to their own `~/.claude/settings.json`.

Auto-update for everyone was the hard requirement, and it is what forced this. Third-party marketplaces ship with auto-update **off**; the only ways to turn it on for a whole team are the per-user `/plugin` toggle, `extraKnownMarketplaces[name].autoUpdate` in a settings file, or Claude's org-level plugin distribution. Of those, only a settings file needs no administrator. And Claude Code's background refresh deliberately disables git credential helpers, so a **private** repo's auto-update pull cannot authenticate over HTTPS — it falls back to a full re-clone that the docs warn "may fail intermittently." Since the audience includes non-developers with no GitHub account, no SSH key, and no repo access, a private repo would have meant auto-update silently rotting for exactly the people least able to notice or fix it.

## Considered options

- **Private repo + Claude org plugin distribution** (`claude.ai/admin-settings/plugins`). Genuinely the cleanest fit — the Claude GitHub App reads the private repo and packages plugins, so nobody needs repo access, and updates are handled by org sync. Rejected for now only because it requires a Claude org admin: Passion is on a Claude Team plan, but our `organizationRole` is `user`. Worth revisiting if that changes.
- **Private repo + SSH remotes.** Auto-update would work only for people with a repo-authorised key in `ssh-agent`, which means adding every person to the repo — the thing we set out to avoid.

## Consequences

Everything in the repo is world-readable forever, including git history, so making it private later does not unpublish anything. Nothing internal may be committed: no hostnames, credentials, ticket contents, or notes on how our systems are configured. Skills that need those read them from the environment at runtime.

**Commit metadata is content.** Every commit publishes its author's email, and "world-readable forever, including git history" applies to that field exactly as it applies to a file. So this repo sets a **repo-local** identity to a GitHub `users.noreply.github.com` address, and `marketplace.json` carries `owner.name` without `owner.email`: the team is named, no harvestable work address is. A contributor's first act is `git config user.email` inside their clone — before the first commit, because that is the one that cannot be edited later. This is the whole reason the setting is repo-local rather than global: nobody should have to change how they commit everywhere else to contribute here.

*This was breached. A real project key sat in `jira:ticket`'s frontmatter and its `Variables` block, and shipped publicly through every CI run, because the `secrets` check had patterns for hosts, tokens, and private keys but none for an issue key. The [0020](0020-model-invocation-is-a-contract-between-skills.md) pass found it — it was the only issue-key-shaped token in the repo that was not the `ABC` placeholder every other skill uses. `secrets` now fails on `[A-Z]{2,10}-\d+` outside a small allowlist, so the same leak cannot recur silently. Two softer hits went with it: `sprint_report.py` hardcoded our configured Jira workflow states, which is a note on how our systems are configured, and now buckets on Jira's built-in `statusCategory` instead — that leaks nothing and needs no configuration on any instance. A `rock:status` line described an exception firing in our live instance since 2021 with a specific occurrence count, and a `rock:data` worked example carried a fabricated attendance figure dated to the Sunday just past, which reads as a real headcount. Both are gone. The lesson is that the constraint's soft edge — observations about how our systems behave and are configured — is where it actually gets crossed, and that edge is much harder to write a pattern for than a credential.*
